## 1. Описание проекта
Данный репозиторий содержит материалы практической работы по моделированию бизнес-процесса оформления заказа в интернет-магазине с использованием языка UML (Unified Modeling Language).

### Структура репозитория
- `sequence_diagram.puml` – исходный код диаграммы последовательности (PlantUML).
- `sequence_diagram.png` – сгенерированное изображение диаграммы последовательности.
- `state_diagram.puml` – исходный код диаграммы состояний объекта "Заказ" (PlantUML).
- `state_diagram.png` – сгенерированное изображение диаграммы состояний.
- `README.md` – этот файл с описанием и пояснительной запиской.

## 2. Описание диаграмм

### 2.1. Диаграмма последовательности (Sequence Diagram)
Моделирует сценарий "Оформление заказа и оплата". 
**Участники:** Покупатель, Корзина (Система), Система оплаты, Склад.
Диаграмма включает фрагменты `alt` для обработки альтернативных сценариев:
1. Наличие или отсутствие товара на складе (предотвращение overselling).
2. Успешный или неуспешный результат транзакции в платёжном шлюзе.

### 2.2. Диаграмма состояний (State Machine Diagram)
Описывает полный жизненный цикл сущности "Заказ". 
Отражает переходы между состояниями: `Создан` → `Ожидает оплаты` → `Оплачен` → `Собирается` → `Отправлен` → `Доставлен`, а также ветвление в состояние `Отменён` при возникновении ошибок, таймаутов или обнаружении брака.

## 3. Пояснительная записка

**Моделируемые сценарии:**  
В работе смоделирован основной успешный сценарий (Main Success Scenario) и альтернативные сценарии процесса покупки. Диаграмма последовательности охватывает критический путь пользователя: от инициации оформления заказа до финального уведомления. Ключевым аспектом является взаимодействие между фронтенд-системой («Корзина»), внешним сервисом («Система оплаты») и бэкенд-логикой («Склад»).

**Обоснование выбора сообщений:**  
Последовательность сообщений выбрана в соответствии с реальными архитектурными паттернами e-commerce систем:
* *Проверка наличия* предшествует любым другим действиям, чтобы не вводить пользователя в заблуждение.
* *Резервирование* выделяется в отдельный шаг с таймаутом. Это необходимо для того, чтобы товар не был продан другому покупателю, пока текущий вводит данные карты, но при этом склад не был заблокирован навечно при брошенной корзине.
* *Подтверждение оплаты* инициирует цепочку сообщений на склад, что гарантирует принцип идемпотентности: сборка начинается только после гарантированного получения средств.

**Обоснование выбора состояний объекта «Заказ»:**  
Детализация состояний обеспечивает прозрачность бизнес-процесса и позволяет корректно обрабатывать краевые случаи (edge cases):
* **Ожидает оплаты**: критически важное промежуточное состояние. Товар зарезервирован, но сделка не завершена. Из этого состояния возможен переход в **Отменён** по таймауту, что освобождает складские остатки.
* **Собирается** и **Отправлен**: детализация процесса исполнения заказа для отслеживания прогресса.
* **Отменён**: альтернативное терминальное состояние. В него возможен переход не только из "Ожидает оплаты", но и из "Собирается" (например, при обнаружении брака), что требует автоматического инициирования процесса возврата средств.
